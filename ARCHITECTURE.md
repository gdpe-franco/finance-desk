# Internal Transactions System architecture

## Scope

Internal Transactions System is a single Spring Boot application for internal account transfers. The MVP uses Java 21, Spring Boot 3, MySQL 8, and a REST API. It does not include a frontend, external payment rails, authentication, messaging, or distributed services.

## Layers

```text
web → application → domain
          ↑
infrastructure (implements application persistence ports)
```

- `domain` owns account, transfer, and ledger rules and types; it has no Spring or HTTP dependencies.
- `application` coordinates use cases and defines persistence ports where they isolate persistence behavior.
- `infrastructure.persistence` implements those ports with Spring Data JPA and MySQL.
- `web` maps HTTP requests/responses and validation to application use cases.

Keep this as one deployable application. Add abstractions only where they separate business behavior from infrastructure or provide a concrete persistence capability such as locking.

## Money and accounts

- Store money as `BigDecimal` and MySQL `DECIMAL(19,2)`; reject more than two fractional digits rather than rounding.
- Accept only MXN, USD, and EUR for the MVP; all have two decimal places here.
- Account creation through REST starts with a zero balance and ACTIVE status. Funded demo accounts are loaded only by an explicit local development fixture; their opening funds are outside the transfer ledger.
- Account numbers are generated by the server as unique 18-digit CLABE-format identifiers with a synthetic `999999` institution/plaza prefix and standard check digit. This internal demo does not participate in SPEI and generated values must not be presented as real or externally routable CLABEs. Balances cannot be negative, and the maximum value is bounded by the database precision.
- Account clients may update only the owner name; account number and currency remain fixed, and balance and status are not editable through account endpoints.

## Transfer, idempotency, and failure contract

- Reject malformed requests at the HTTP boundary; they do not create transfer records.
- Require a UUID `Idempotency-Key`. A key is unique in the database and bound to normalized source, destination, amount, and currency input. Repeating the same request returns its stored outcome; reusing the key for different input returns `409 Conflict`.
- A repeated key returns the stored terminal result. Repeating a failed business request returns the same failure; callers need a new key for a corrected request.
- Persist business failures so attempts remain queryable. A failure code is stored on the transfer for stable replay. Unexpected failures are not misreported as business failures.
- Register a transfer as PENDING in a short transaction. Process it in a separate transaction that locks the transfer row, then both account rows ordered by ascending account ID. Validate all rules before changing balances. Success updates both balances, inserts exactly one DEBIT and one CREDIT ledger entry, and marks the transfer COMPLETED in that same transaction. A business-rule failure marks the transfer FAILED without changing balances or ledger.
- If unexpected processing fails, that transaction rolls back and leaves the attempt PENDING. A matching retry resumes it under the transfer-row lock; do not record unexpected errors as FAILED in a separate transaction. Registration failures return a safe `500` with a stable code and no transfer ID; processing failures return a stable code and registered transfer ID when known. There is no background recovery job in the MVP.
- Concurrent account updates use pessimistic row locks acquired in a deterministic order. The database remains the final authority for unique constraints and nonnegative balances.
- Ledger entries are append-only in application behavior; database uniqueness on `(transfer_id, type)` prevents duplicate debit/credit entries.

## API behavior

- Successful account creation returns `201 Created`; missing resources return `404`.
- Validation errors use Spring `ProblemDetail` responses. Business rule failures use stable error codes; idempotency payload conflicts return `409`.
- Malformed transfer requests return `400` and create no attempt. Well-formed requests rejected by transfer business rules return `422` with the persisted transfer ID and failure code.
- Ignore unknown JSON request properties. Request DTOs must not bind caller-provided account numbers, balances, or statuses into domain/persistence models.
- Ledger reads are paginated with a deterministic order.

## Decisions deferred

OpenAPI is added during release-readiness work. Authentication, deposits, outbox/event publishing, Kafka, Redis, scheduled recovery, and production-grade operational telemetry are outside the MVP.
